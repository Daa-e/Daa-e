# TinyPaw Adventures

2~4인이 전기 울타리를 피하며 타일을 점령하는 3D 멀티플레이 땅따먹기 게임입니다.

| | |
|---|---|
| 기간 | 2026.06 ~ 2026.07 |
| 팀 | 6인 |
| 환경 | UE5 · C++ · EOS |
| 담당 | EOS 세션 생성, 검색, 참가 · 서버 권한 로비 상태와 Ready 검증 · 플레이어 외형 동기화 · 캐릭터와 타일 시스템 · 로비와 결과 UI |

팀 저장소는 비공개입니다.

## 세션 관리를 GameInstanceSubsystem으로 분리

- 목표: GameInstance 한 곳에 EOS 로그인과 방 생성, 검색, 참가가 섞여 있었습니다. 방 정보와 검색 결과를 UI에 전달할 구조가 필요했습니다.
- 설계: 로그인은 GameInstance에 두고, 방 생성, 검색, 참가, 게임 시작을 세션 서브시스템으로 옮겼습니다. 방 정보는 EOS 세션 설정에 광고하고, 결과는 완료 델리게이트로 UI에 전달합니다.
- 결과: UI는 델리게이트만 받아 방 흐름을 처리합니다. 서브시스템은 GameInstance와 수명이 같아 맵을 옮겨도 유지됩니다.

## PlayerState 복제와 델리게이트로 외형 동기화

- 목표: 서버가 정한 색상이 모든 화면의 캐릭터에 같게 보여야 했고, 캐릭터 생성 뒤 PlayerState가 도착하는 순서는 보장되지 않았습니다.
- 설계: PlayerId, PlayerColor, CharacterMaterialIndex를 `ReplicatedUsing`으로 두고 서버에서만 바꿉니다. 각 OnRep이 변경 델리게이트를 Broadcast하면 캐릭터가 동적 머티리얼 색을 갱신합니다. 캐릭터는 BeginPlay와 `OnRep_PlayerState` 양쪽에서 구독합니다.
- 결과: PlayerState가 늦게 와도 외형이 맞춰지고, PlayerState는 캐릭터 클래스를 모른 채 변경 사실만 알립니다.

## 서버 확정 상태만 로비 UI에 반영

- 문제: 색상과 Ready를 누르면 클라이언트가 서버 응답 전에 화면을 먼저 바꿔, 거부된 선택이 남을 수 있었습니다. 슬롯 번호만으로 요청을 받으면 남의 슬롯도 바꿀 수 있는 구조는 막아야 했습니다.
- 해결: 클라이언트 선반영을 지우고 SlotIndex와 RequestingPlayerId를 서버 RPC로 보냈습니다. 서버는 슬롯 주인과 요청자의 PlayerId가 다르면 거부하고, UI는 `OnRep_LobbyPlayers`로만 갱신합니다.
- 결과: 거부된 요청이 화면에 남지 않고, 열린 메뉴는 서버가 확정한 슬롯 상태로 다시 그려집니다.

## 동점, 0점, 재접속에도 로비와 랭킹 유지

- 문제: 개인 순위에 동점 분기가 없어 선두에게 승점이 갈 수 있었고, 0점 플레이어는 순위에서 빠졌습니다. 재접속한 플레이어를 새 슬롯으로 받으면 슬롯이 중복되고 Ready와 색이 초기화됐습니다.
- 해결: 상위 두 점수가 같으면 승점 없이 다음 라운드로 넘깁니다. 랭킹을 CurrentPlayers로 먼저 만들어 0점도 포함하고, PostLogin에서 같은 PlayerId(없으면 이름)의 기존 슬롯을 찾아 Ready와 색을 이어받게 했습니다.
- 결과: 동점은 무승부로 처리되고, 0점도 순위에 남으며, 재접속 뒤 로비 상태가 유지됩니다. 서버 로그로 확인했습니다. 팀전 동점 규칙은 팀원이 구현했습니다.

## 캐릭터 미선택 Ready와 시작 조건 차단

- 문제: 캐릭터를 고르지 않아도 Ready가 되어 시작 조건에 포함될 수 있었습니다. 서버의 Ready 처리와 전원 Ready 판정 모두 `bIsReady`만 봤습니다.
- 해결: 서버 Ready 처리 두 곳, 시작 판정, 클라이언트 버튼 처리 네 지점에서 PlayerColor가 None인지 같은 기준으로 검사합니다.
- 결과: 미선택 플레이어는 Ready가 되지 않습니다. 클라이언트는 요청을 보내지 않고, 서버는 거부 로그를 남깁니다.
